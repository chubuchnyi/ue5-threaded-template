# MotionLink Prototype

## Что строим и зачем

Минимальный сквозной прототип конвейера «физика UE5 → межпоточная передача → сеть → контроллер платформы». Железа нет, контроллер заменён программной заглушкой.

Цель прототипа – **не функциональность, а тренировка**. Три вещи, которые он должен доказать:

1. Данные с физического тика уходят на свой поток без блокировки игрового потока и без обращения к `UObject` извне.
2. Поток фиксированной частоты 1 кГц держится на Windows, и его джиттер измерен, а не предположен.
3. Проект UE собирается, отлаживается и профилируется – включая Insights и подключение отладчика.

Это учебный стенд. Красота, полнота и переиспользуемость не требуются. Требуется, чтобы всё работало и было измерено.

## Явно вне области

Не реализуем, даже если кажется, что «легко добавить»:

- обратная кинематика и любая конкретная механика;
- настоящий motion cueing – только скелет фильтра с одним коэффициентом;
- VR, компенсация трекинга;
- reverse engineering чужих игр;
- реальные приводы, EtherCAT, CAN, UART;
- безопасность, E-stop, состояния FAULT сверх минимума;
- красивый UI.

Если задача тянет за собой что-то из этого списка – остановиться и спросить, а не расширять область.

## Архитектура прототипа

```
┌─────────────────────────────────────────────┐
│ UE5 Editor / Standalone                     │
│                                             │
│  Physics thread (async tick)                │
│    └─ TelemetrySource → SPSC ring           │
│                                             │
│  MotionWorker (FRunnable, 1 кГц)            │
│    ├─ наблюдатель const-accel               │
│    ├─ скелет cueing + лимитер               │
│    └─ UDP tx / rx                           │
│                                             │
│  Game thread                                │
│    └─ отладочный оверлей (только чтение)    │
└──────────────┬──────────────────────────────┘
               │ UDP localhost:5005 / 5006
┌──────────────▼──────────────────────────────┐
│ controller_sim (отдельный процесс, без UE)  │
│    ├─ приём, проверка CRC и seq             │
│    ├─ эхо seq + t_rx + t_tx                 │
│    ├─ модель привода: апериодическое звено  │
│    └─ CSV-лог и статистика в консоль        │
└─────────────────────────────────────────────┘
```

Два процесса. Заглушка контроллера – обычный C++ без зависимостей от движка, собирается отдельным CMake-проектом. Это позволяет разрабатывать и тестировать протокол до того, как соберётся UE.

## Этапы

Строго по порядку. Каждый этап заканчивается работающим артефактом.

### Этап 0 – протокол

`shared/motion_protocol.h` – один заголовок, без зависимостей, используется обоими проектами.

- `SetpointFrame`: magic, proto_ver, msg_type, seq, t_tx_ns, flags, pose[6], vel[6], crc32.
- `FeedbackFrame`: seq (эхо), t_rx_ns, t_tx_ns, measured_pose[6], state, fault_mask, limiter_active.
- Фиксированный размер, `#pragma pack`, little-endian, `static_assert` на размер структуры.
- CRC32 – табличная реализация в том же заголовке.

Готово, когда: заголовок компилируется обоими компиляторами, `static_assert` проходит.

### Этап 1 – заглушка контроллера

`tools/controller_sim/` – CMake-проект, консольное приложение.

- Приём UDP на 5005, отправка эха на 5006.
- Проверка CRC, детект пропусков и переупорядочивания по `seq`.
- Ресемплинг входа на свой тик 2 кГц по `t_tx_ns`, а не по моменту приёма.
- Модель привода: апериодическое звено первого порядка с постоянной времени из аргумента командной строки.
- Watchdog: нет валидного кадра дольше 5 периодов – рампа в нейтраль за 500 мс, состояние `LIMITED` → `PARK`.
- Статистика раз в секунду в консоль: частота приёма, доля потерь, джиттер интервалов (p50/p99/max), заполненность.
- CSV-лог всех кадров.

Готово, когда: генератор-заглушка шлёт синус, sim принимает и показывает статистику; при остановке генератора отрабатывает watchdog.

### Этап 2 – каркас плагина UE

`Plugins/MotionLink/` – плагин, `LoadingPhase: PreDefault`.

- `UMotionLinkSubsystem : UGameInstanceSubsystem` – владеет потоком.
- `FMotionWorker : FRunnable`, приоритет `TPri_TimeCritical`, аффинити на выделенное ядро.
- Таймер: `CreateWaitableTimerExW` с `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION`, период 1 мс.
- Пока никакой физики – поток гонит синтетический синус в UDP.
- Отладочный оверлей на игровом потоке: частота, seq, RTT, состояние. Только чтение из атомиков.

Готово, когда: `controller_sim` принимает поток из UE, статистика показывает стабильные 1000 Гц.

Этот этап – главный по цели «потренироваться в сборке». Здесь вы первый раз проходите весь путь: генерация проекта, сборка, запуск, подключение отладчика.

### Этап 3 – SPSC-кольцо и реальная телеметрия

- `TelemetryRing` – кольцо на двух атомарных индексах, каждый `alignas(64)`. Не `TQueue`: смысл в том, чтобы написать самому и понимать порядок памяти.
- Включить async physics tick в настройках проекта.
- `UTelemetrySourceComponent` – снимает состояние на физическом тике и пишет в кольцо.
- Тестовая сцена: простой актор с физическим телом, которым можно управлять, либо Chaos Vehicle из шаблона. Достаточно, чтобы были ненулевые ускорения.
- Наблюдатель const-accel в `MotionWorker`: интегрирование на 1 кГц, коррекция невязки при приходе сэмпла, размазанная по нескольким миллисекундам.

Готово, когда: движение объекта в сцене видно в CSV на стороне `controller_sim`, при просадке FPS выход остаётся гладким.

### Этап 4 – скелет cueing и лимитер

- Washout: ФВЧ на трансляции, ФНЧ на tilt coordination. Один коэффициент на канал, всё через CVar.
- Лимитер: масштабирование всего вектора отклонения от нейтрали одним коэффициентом, без покомпонентного клампа. Флаг `limiter_active` в обратный поток.
- Ограничение по скорости и рывку.

Готово, когда: коэффициенты меняются из консоли на лету, лимитер срабатывает и это видно в логе.

### Этап 5 – измерения

Это то, ради чего всё затевалось.

- `TRACE_CPUPROFILER_EVENT_SCOPE` на физ-тике, тике воркера, отправке.
- `TRACE_COUNTER_SET` на джиттер, глубину кольца, RTT, возраст последнего сэмпла.
- Скрипт разбора CSV: гистограммы интервалов, RTT, оценка задержки от физ-тика до приёма контроллером.
- Короткий отчёт `docs/measurements.md` с числами и графиками.

Готово, когда: есть трасса Insights, где видны все потоки, и есть числа по джиттеру и задержке.

## Правила кода

### Горячий путь – это `FMotionWorker::Run`, физ-тик и всё, что они вызывают

Пять запретов, нарушение любого – ошибка ревью:

1. Никаких аллокаций после старта. Всё преаллоцировано в `Init()`.
2. Никаких мьютексов. Только атомики и SPSC-кольцо.
3. Никаких блокирующих вызовов – файлы, `UE_LOG`, синхронные сокеты.
4. Никаких исключений. Коды возврата.
5. Никаких `UObject`, `FString`, `TSharedPtr`. Только POD.

Логирование из горячего пути – через кольцо, вывод из фонового потока.

### Владение данными

- `UObject` трогаются только с игрового потока. Ставить `check(IsInGameThread())` в местах, где это обязательно.
- Между потоками ходят только копии POD-структур.
- Каждое разделяемое поле – либо атомик с явным `memory_order`, либо элемент кольца. Третьего варианта нет.
- Оверлей на игровом потоке читает атомики и ничего не пишет.

### Порядок памяти

Писать явно, не полагаться на умолчания. В кольце: `release` на публикации индекса писателя, `acquire` на чтении. В комментарии к каждому нетривиальному атомику – зачем именно такой порядок.

### Конфигурация

Всё, что настраивается, – в CVar с префиксом `motion.`. Ни одной магической константы в коде. Список CVar поддерживать в `docs/cvars.md`.

## Сборка и отладка

### Проект UE

- Конфигурация `Development Editor`, Visual Studio.
- Правый клик по `.uproject` → Generate Visual Studio project files после любого изменения структуры модулей.
- Символы движка обязательны, иначе стек нечитаем.
- `UE.natvis` подключить, иначе `TArray` в отладчике – сырая память.

### Live Coding

Работает для тел функций. Правка заголовков, добавление `UPROPERTY`, изменение размера класса – ломает. При странном поведении после серии горячих правок первое действие – перезапуск редактора, а не отладка.

### Профилирование

Только Standalone или packaged Development. В PIE замеры недостоверны: другой мир, редактор держит ресурсы.

```
UnrealEditor.exe MotionProto.uproject -game -trace=cpu,frame,counters,bookmark
```

### Заглушка контроллера

```
cmake -B build -S tools/controller_sim
cmake --build build --config Release
./build/Release/controller_sim --tau 0.02 --csv run.csv
```

### Настройки системы для замеров

Отключить core parking и C-states, вынести прерывания сетевого адаптера на другое ядро, закрепить `MotionWorker` на выделенном ядре. Без этого числа по джиттеру не имеют смысла.

## Критерии готовности

Прототип считается сделанным, когда выполнены все пункты:

- [ ] `controller_sim` принимает поток из UE на 1 кГц, потери меньше 0.1%
- [ ] p99 джиттера интервала отправки измерен и записан
- [ ] искусственная просадка FPS (`t.MaxFPS 20`) не даёт разрывов в выходном сигнале
- [ ] убийство процесса UE приводит к отработке watchdog и рампе в нейтраль
- [ ] задержка от физ-тика до приёма контроллером измерена
- [ ] трасса Insights показывает все потоки, физ-тик и тик воркера видны как именованные события
- [ ] `check(IsInGameThread())` расставлены и ни разу не срабатывают
- [ ] `docs/measurements.md` содержит числа и выводы

## Как вести работу

- Один этап – одна ветка, один PR. Не начинать следующий, пока предыдущий не даёт работающий артефакт.
- После каждого этапа обновлять `docs/measurements.md`, даже если там пока одна строка.
- Если возникает выбор между «сделать правильно» и «сделать минимально» – минимально, но с комментарием `// PROTOTYPE:` и строкой в `docs/shortcuts.md`.
- Числа в документации – только измеренные. Оценки помечать явно.
